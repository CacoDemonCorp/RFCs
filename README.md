# Технические решения CacoDemonCorp

Этот репозиторий предназначен для совместного обсуждения и фиксации решений по общей инфраструктуре CacoDemonCorp.

В каждом документе сохраняются контекст, рассмотренные альтернативы, их преимущества и недостатки, итоговый выбор и его последствия. Благодаря этому существенное изменение можно целиком обсудить в одном месте, а позднее понять причины устройства системы.

## RFC и ADR

**RFC (Request for Comments):** предложение, которое ещё обсуждается. Оно описывает проблему, требования и возможные решения. Участники оставляют замечания во время ревью.

**ADR (Architecture Decision Record):** запись о принятом архитектурном решении. Она сохраняет контекст, выбранный вариант, причины выбора и его последствия.

В этом репозитории RFC и ADR являются стадиями одного документа:

1. Документ создаётся со статусом `Предложено` и обсуждается в pull request.
2. Замечания оставляются к конкретным строкам; при необходимости документ изменяется.
3. После завершения обсуждения статус меняется на `Принято` или `Отклонено`.
4. Документ сохраняется в репозитории независимо от результата, чтобы не потерять причины решения.

Такой процесс остаётся достаточно лёгким для небольшой команды, но делает существенные решения прозрачными и проверяемыми.

## Когда нужен RFC

RFC имеет смысл, если решение:

- затрагивает общую инфраструктуру или нескольких участников;
- меняет границы владения, ответственности или доступа;
- влияет на надёжность, безопасность, сопровождение или развёртывание;
- имеет несколько реалистичных вариантов с разными компромиссами;
- будет важно понимать в будущем.

Небольшие локальные и легко обратимые изменения можно обсуждать в обычном pull request без отдельного RFC.

## Как предложить решение

1. Создать отдельную ветку.
2. Скопировать [`template.md`](template.md) в каталог [`decisions`](decisions) и заполнить документ.
3. Открыть draft pull request.
4. Попросить всех заинтересованных участников проверить факты, критерии, альтернативы и последствия.
5. Обновлять предложение по результатам обсуждения, не удаляя значимые компромиссы.
6. Зафиксировать итоговый статус и только после этого завершить pull request.

Фактическая неизвестность указывается в том разделе, где она влияет на сравнение или реализацию. Отдельный список открытых вопросов не используется: без контекста такие списки быстро теряют связь с решением.

При ревью полезнее привязывать замечание к конкретному месту документа и указывать, что именно следует изменить:

- неверный или неполный факт;
- отсутствующий критерий выбора;
- нерассмотренная реалистичная альтернатива;
- неверно описанное преимущество, недостаток или последствие;
- причина, по которой предложенный вывод не следует из сравнения.

## Статусы

- `Предложено`: решение обсуждается.
- `Принято`: решение согласовано и может быть реализовано.
- `Отклонено`: предложение рассмотрено, но не выбрано.
- `Заменено`: вместо этого решения позднее принято другое. Новое решение указывается ссылкой.
